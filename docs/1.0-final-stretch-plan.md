# Axial 1.0 — Final Stretch Plan (v2)

Created 2026-09-18. Builds on [docs/1.0-release-plan.md](1.0-release-plan.md)
(the "spine" plan) — Phases 0–5 there are done or in flight; this doc defines
the **feature scope for 1.0**, a **logic-issue audit** of the activation
paths, the new update experience, an **agent-parallel execution strategy**,
and a launch plan. Read the spine plan first; nothing here changes its
decisions.

**The 1.0 thesis:** Axial is already the only Factorio mod manager with
dependency planning, SHA1-verified downloads, and switchable packs. 1.0 should
say two things loudly: *"it's safe"* (integrity, crash recovery, signed
updates) and *"it knows your game"* (detection, launch, external-change sync).
Everything below serves one of those two sentences — and the P0 audit fixes
are what make the first claim true.

Estimate: **~6 weeks** from 2026-09-18 (P0 fixes ~1 wk, Tier A features
~1.5 wk, engineering spine ~2.5 wk, RC + release ~1.5 wk). Cut order is
explicit at the bottom.

## Part 0 — Logic-issue audit (P0 correctness fixes)

Found 2026-09-18 by reading the activation paths after a user report:
*"activating the Vanilla pack leaves Space Age and Quality enabled."* Fix
these **before any feature work** — they are correctness, and Phase 6b will
re-test all of them.

### P0-1. Vanilla leaves unlisted mods enabled — the reported bug ✅ root-caused

**Root cause:** `disable_all_mods` (`mod_store.rs:727`) only flips the
`enabled` flag on entries **already present** in `mod-list.json`. Mods whose
zips sit in the mods dir but which have **no entry** in `mod-list.json` are
not touched — and Factorio treats disk-present-but-unlisted mods as *enabled*
and catalogues them at next launch. The game-bundled expansion zips
(`space-age`, `quality`) hit exactly this hole (fresh DLC install, game
update that drops new zips, hand-edited or pack-rewritten `mod-list.json`).
Result: "Vanilla" silently boots with the expansion on — and `quality` is a
hard dependency of `space-age`, so both come on, sometimes colliding with
whatever the user expected.

**Fix (one path, not a patch):** make Vanilla use the same reconciliation as
packs — scan the mods dir, then write the target state with
`replace_mod_list`:

- New pure function in `packs.rs`: `vanilla_entries(disk_names) -> Vec<(String, bool)>`
  = every disk mod disabled, except `base` (and see P0-6 for the expansion
  policy decision). Unit-test it like `compose_entries`.
- `activate_vanilla` (`packs.rs:495`) scans via `zip_cache` (same pattern as
  `finalize_now`) and calls `replace_mod_list`; **delete** `disable_all_mods`
  or reduce it to a wrapper so the two code paths can't drift again.
- Side benefit: `replace_mod_list` guarantees a canonical enabled `base`
  entry even when `mod-list.json` was missing/corrupt — `disable_all_mods`
  never did.
- Regression test (repo convention, `mod_store.rs`/`packs.rs`): `mod-list.json`
  *without* a `space-age` entry + `space-age_1.0.zip` on disk → after Vanilla,
  the entry exists and is `enabled: false`.

### P0-2. Finalize enables wrong versions after failed downloads

`compose_entries` (`packs.rs:249`) matches pack mods to disk by **name
only**. If a pack download fails or is cancelled, `finalize_now`
(`packs.rs:446`) happily enables whatever version is on disk — silently
deviating from the pack manifest. Fix:

- `compose_entries` takes `disk_versions: &HashMap<String, String>` too;
  a present-but-wrong-version mod is written **disabled** and returned in a
  new `version_mismatch: Vec<PackMod>` list.
- `PackActivatedPayload` carries it; `PackModal`/queue shows "activated, but
  N mods are the wrong version — retry" instead of a clean success.
- Tests: match, mismatch-disables-and-reports, absent-stays-off.

### P0-3. Pack downloads bypass SHA1 verification

Pack activation enqueues with `expected_sha1: None` (`packs.rs:337` — the
manifest carries no hash, comment says verification "degrades to the
zip-structure check"). That undercuts the Phase 1 guarantee on exactly the
flow 1.0 is advertising. Fix: before enqueue, look the release up via the
existing portal client (`ModRelease.sha1`, already parsed) and pass it through;
`None` only if the portal has no hash. Cache lookups make this cheap.
Update the stale comment.

### P0-4. Activation race: no serialization between activate / vanilla / finalize

`activate` and `activate_vanilla` both rewrite `mod-list.json`, and pack
finalization runs later on `tauri::async_runtime`. An in-flight finalize can
overwrite a just-activated Vanilla state (and re-persist the pack's
`active_pack_id` over `"vanilla"`); two rapid toggle flips can interleave
writes. Fix: an `Arc<Mutex<()>>` (or `tokio::sync::Mutex`) "activation lock"
on `AppState` held across each activate/vanilla/finalize body. Vanilla must
**wait** for an in-flight finalize rather than just clearing
`pending_activation` (clearing is still correct for *queued* pending
activations — keep that, but under the lock). Test: hard to unit-test;
document the invariant and verify in the Phase 7 torture list ("pack switch
and Vanilla clicked back-to-back").

### P0-5. State-consistency sweep (small, ride along with the above)

Checked while auditing; each is small but none is free:

- [ ] `disable_all_mods` writes `enabled: false` onto entries with no
      readable `name` — fine — but a `mod-list.json` where `mods` is not an
      array is silently left untouched (no error). `load_mod_list_for_write`
      should reject that shape like it rejects corrupt JSON.
- [ ] `activate_vanilla` persists `active_pack_id = "vanilla"` even when the
      mods-dir write failed? No — the `?` on `disable_all_mods` returns
      first. Correct as written; add a test pinning that order so a refactor
      can't invert it.
- [ ] `updates.rs` update-check and the resolver evaluate deps against
      *installed* mods regardless of enabled state — a disabled incompatible
      mod suppresses no conflict warnings. Revisit as part of A2
      (reverse-deps) with the same parsed graph.
- [ ] Crash-recovery re-enqueue runs at startup before the user picks a
      pack; if the user immediately activates Vanilla, recovered downloads
      still land and re-enable nothing (they only download) — fine, but the
      queue's "Finished" entries then lie about being useful. Cosmetic;
      note only.

**Estimate for all of Part 0:** ~4–5 days including tests. The audit itself
continues as Phase 6b of the spine plan — these are the found-so-far items,
found *early* because a user hit one.

## Part I — Feature tier for 1.0

Tier A ships unless something is genuinely broken. Tier B is pulled in order
of the list while time remains. Tier C is the post-1.0 parking lot — listed so
we can point contributors at it, not so we feel tempted.

Every feature follows the standing rules: thin commands, logic in
`core/services/`, types in `models.rs`, typed wrapper in `lib/api.ts`, tests
Rust-side in the same file, `ASSUMPTION (...)` comments for any new upstream
API assumption.

### A0. Vanilla & expansion policy (product decision, closes the reported class)

The P0-1 fix makes Vanilla mean *base only*. Space Age owners also need the
other vanilla: **base + `space-age` + `quality`, nothing else.**

- Detect expansion presence by the `space-age` zip on disk (no purchase
  check, no auth — the zip only exists if the user owns the DLC).
- If present, Packs page shows **two** built-ins pinned first:
  `Vanilla` and `Vanilla: Space Age`; Quick Access the same, active one with
  the green StatusDot.
- `activate_vanilla(expansion: bool)` command signature; `vanilla_entries`
  gains the same flag. Tests for both flavors + expansion-zip-absent fallback.
- This also resolves the "sometimes incompatible" complaint structurally:
  users who want no expansion can now *have* no expansion, explicitly.

**Effort:** ~1 day on top of P0-1 (same code path).

### A1. External mod-list change sync (watch the game)

**Why:** Factorio itself edits `mod-list.json` (in-game mod toggles, savegame
"missing mods" prompts) and users drag zips into the mods dir by hand. Today
Axial's Installed view can silently disagree with disk. A 1.0 that *manages*
the mods dir must not stale-cache it. It also pairs with P0-4: the watcher is
what notices when the game clobbers Axial's writes.

- `notify` crate watches the mods directory (`mod-list.json` + zip
  create/delete), debounced (~500 ms), spawned via `tauri::async_runtime`.
- On change: diff a cheap fingerprint (mtime + size of `mod-list.json`, zip
  name set) against the last known state; only on real change re-scan and emit
  a new `installed-changed` payload with a `reason: "external" | "axial"`
  field.
- Frontend: `lib/events.ts` already owns the listener; the store refetches.
  If the external change happened *while a pack was active*, show a subtle
  "mods changed outside Axial — state may differ from pack X" hint, not a
  modal. No lock files, no write watching beyond the two patterns above.
- Tests: fingerprint diff logic pure-function tested; watcher smoke-tested
  manually on all three OSes (Phase 7).

**Effort:** ~2 days. **Risk:** low. The single most important missing feature.

### A2. Reverse-dependency guard on uninstall & disable

**Why:** the resolver already models the dep graph forward; uninstalling a mod
that others depend on currently breaks those mods until the next Factorio
launch complains. Cheap to add, high perceived intelligence.

- `deps.rs`/`resolver.rs`: build the reverse edge set from installed mods'
  parsed dependency strings (already mirrored via `mirror_client` enrichment).
- `mod_store.rs`: new `uninstall_impact(name) -> Vec<String>` (dependents that
  would be left broken) called by the uninstall path; command returns it.
- UI: uninstall button flow — if impact is non-empty, the existing
  `useConfirm` dialog lists the dependents ("Removing Krastorio2 leaves 3
  mods broken"). Still one click; we inform, we don't block.
- Tests in `resolver.rs` (tokio): fan-out, cycles, hidden-required (`~`)
  dependents.

**Effort:** ~1.5 days. **Risk:** low — reuse of existing parsing.

### A3. Changelog preview on update

**Why:** "Update all" today is a blind trust button. Showing *what changed*
turns it into a feature people talk about.

- First **verify against the live API** whether
  `https://mods.factorio.com/api/mods/<name>/changelog` exists and is
  unauthenticated (record an `ASSUMPTION (...)`; fall back to parsing the
  `<name>/changelog.txt` attachment link if the JSON route doesn't exist).
- New `changelog` command in `portal_client.rs` → tolerant DTO (version +
  date + bullet list). Cache in `index_client` like everything else.
- UI: the VersionsModal and the bulk-update confirmation gain a
  changelog section for the newest release; expandable installed rows (2a)
  show the installed→latest delta when an update exists.
- Offline failure → muted "changelog unavailable", never a toast (same rule
  as row-expansion summaries).

**Effort:** ~2 days. **Risk:** medium (upstream format not yet verified) —
hence the spike first.

### A4. Mods-dir hygiene: orphan detection + size report

**Why:** every Factorio player's mods folder contains ghost zips (`<mod>`
disabled entries pointing at deleted files, old versions left after updates,
`.part` debris from crashes). Axial already scans everything; reporting it is
nearly free and makes the Dashboard feel alive.

- `mod_store.rs`: during the installed scan, collect orphans (zips not
  referenced by `mod-list.json`, zips referenced but missing, stray `.part`
  files) and aggregate per-mod + total directory size.
- Settings → Storage section (already exists): show total size, count of
  orphans, and a "Clean orphans…" action with `useConfirm` that deletes only
  provably-orphaned zips, never anything referenced.
- Dashboard: "Mods storage: 3.2 GB · 4 orphans" stat card, click-through to
  Storage.

**Effort:** ~1.5 days. **Risk:** low; deletion path reuses the existing
uninstall validation (writable probe, atomic-list rewrite untouched).

### A5. Update experience: "Update" pill + release-notes popover

**Why:** the current update UI is a flat banner. The reference design (a small
green **Update** pill that opens a rich release-notes popover) is both more
discoverable and more trustworthy — users see *what* they're getting before
they click. This is Axial's own updater (Phase 3 spine), redesigned.

**Visual spec (from the reference):**

- **Pill:** compact green (`accent` #00CC46) rounded pill with the text
  "Update", placed in the Sidebar header block next to the app logo/version —
  always visible, not a transient banner. A soft pulsing glow (2 s loop) and a
  tiny StatusDot-style dot until first opened; the pulse stops after the user
  has seen the notes. Built from `Button`/`Badge` primitives + `StatusDot`;
  no new accent hues.
- **Popover:** opens anchored to the pill (portal-based, reuse `Modal`'s
  focus-trap + Escape + click-outside machinery as a non-centered variant).
  Content, matching the reference layout: header row "vX.Y.Z Release Notes" +
  release date; scrollable body with bold section headings ("New Features",
  "Fixes") and bulleted entries; footer with a primary "Download & restart"
  button and a secondary "Skip this version" (wires to the existing
  `dismissed_update_version` flow).
- **Animation:** popover scales/fades in from the pill's origin (~150 ms,
  spring-ease); bullets stagger-fade 30 ms apart; pill glow eases out when
  the popover opens. While downloading, the button shows the existing
  `ProgressBar`; on success it morphs to a checkmark with a short countdown
  to restart. **All of it behind `prefers-reduced-motion`.**

**Data plumbing:**

- `scripts/generate-updater-manifest.mjs` already authors `latest.json` — add
  a `notes` field (markdown: the GitHub release body, fetched at manifest
  build time). `@tauri-apps/plugin-updater`'s `check()` already surfaces
  `update.body`; App.tsx currently renders it as plain text.
- New `components/update/UpdatePill.tsx` + `UpdateNotesPopover.tsx`; a tiny
  markdown-lite renderer (bold headings + bullets — no new dependency,
  sanitize by construction). Replaces the `App.tsx` banner; the
  `settings-changed`/dismiss logic moves into it unchanged.
- Check failure / offline: pill hidden, no junk (current behavior keeps).

**Effort:** ~2 days (1 frontend, 0.5 script/CI, 0.5 animation polish).
**Risk:** low. Verified end-to-end in the Phase 8 RC run, since it consumes
the real `latest.json`.

### A6. Command palette (Ctrl+K)

**Why:** creative flagship for the power users who are exactly the audience.
The app already has a single global store and typed API wrappers, so a palette
is pure frontend over existing commands.

- `components/CommandPalette.tsx`: portal modal (reuse `Modal` focus-trap
  machinery), fuzzy search over verbs: navigate tabs, toggle installed mods,
  activate packs (incl. Vanilla flavors), launch Factorio, open queue, open
  Settings, install a mod by name (jumps to Browse results).
- Registered globally in `App.tsx`; Ctrl+K / Cmd+K; arrow-key navigation;
  recent commands first.
- No backend changes at all.

**Effort:** ~2 days. **Risk:** low. Cut first from Tier A if the schedule
slips — it's the only A item that's polish rather than correctness.

### Tier B — pull in this order while time remains

#### B1. Savegame → pack import ("load this save's mods")

The creative differentiator: point Axial at a Factorio save and get a pack
with exactly the mods that save needs. **Feasibility spike first** — the save
zip's `level.dat` is Factorio's custom binary serialization; a community
decoder exists but this is the one item with a real chance of being a rabbit
hole. Spike budget: 1 day. If the mod list can't be read cheaply, fall back to
reading the **save-name → recent-saves heuristic** from the game log, or drop
to 1.1 without guilt. If the spike passes:

- `packs.rs`: `import_pack_from_save(path)` — parse, validate names via
  `plausible_name`, manifest built with resolved latest-compatible versions.
- Settings/Packs: "Import from savegame…" file picker (native dialog is
  already available via Tauri).
- Effort after spike: ~2 days.

#### B2. Official portal downloads via user token

Removes the community-mirror dependency for users willing to authenticate —
the biggest trust upgrade available (and it closes P0-3's cousin: with auth,
every download can be portal-official). Spike: verify the download endpoint's
auth contract against a real token. Then:

- Settings → General: "Factorio account (optional)" — username + token,
  stored in `settings.json` (documented as plaintext, same as Factorio's own
  config), never logged, redacted in any error strings.
- `downloader.rs`: enqueue picks official-URL-with-auth when a token exists,
  mirror otherwise; SHA1 verification is mandatory either way.
- README: mirror note becomes "used only when you haven't connected your
  account".
- Effort: ~2.5 days including tests with a fake auth server.

#### B3. Pack restore points

Before every activation that changes ≥1 mod, write
`profiles/<id>.snapshot.json` of the *current* mod-list state (atomic write,
keep last 3 per pack). Pack modal gains "Restore last state". Pure
`packs.rs` + `mod_store.rs` work, ~1 day, and it makes the no-confirmation
switch UX (deliberate, per `c8afc37`) fully reversible — the right way to
have both speed and safety. **Synergy with P0-4:** the snapshot is taken
inside the activation lock, giving every switch a one-click undo.

#### B4. Bulk enable/disable multi-select on Installed

Checkboxes on rows → selection bar (enable / disable / update selected).
Frontend + one batched command that loops the existing per-mod service call.
~1.5 days.

### Tier C — parking lot (post-1.0, don't touch)

- Mod-local tags, notes, and custom sort/filters
- Download resume (HTTP range) for very large zips
- Scheduled/auto mod-update checks with per-mod pinning
- i18n framework (zh first — the Factorio community would reward it)
- Accent theme picker (`accent` token is already swappable by design)
- Portal favorites sync (needs auth; pairs with B2)
- In-app news feed / release announcements
- Pack sharing as a URL (`axial://import/<base64>`) instead of copy-paste codes
- Screenshot gallery in the details modal
- Per-savegame mod profiles (auto-suggest on save detect)

## Part II — Multi-agent execution strategy

The remaining work decomposes cleanly into small, contract-bounded tasks —
ideal for parallel AI agents (this repo's handoff-prompt pattern, extended).
The main agent is the integrator: it owns `main`, reviews, merges, and runs
the visual gate. **Every agent works in its own git worktree + branch** off
`main`, one feature per agent, so parallel agents never share a working tree.

### Ground rules for every dispatched agent

- Prompt must be self-contained: point at `AGENTS.md`, the relevant section
  of this plan, and the five-step command recipe + test conventions.
- Hard constraints in every prompt: commands stay thin; logic in
  `core/services/`; types in `models.rs`; typed wrapper in `lib/api.ts`;
  Rust tests in the same file; no new crate/npm dependency without stating
  why in the final message; run `cargo test --manifest-path
  src-tauri/Cargo.toml` **and** `pnpm build` before declaring done and paste
  the tail of the output.
- File-ownership map (enforced by task assignment, since agents in separate
  worktrees can't see each other): any file two tasks both need is either
  sequenced into different waves or the task prompt says "additive changes
  only, no renames".
- One conventional commit per task on its branch (`fix(packs): ...`,
  `feat(ui): ...`); the main agent merges with `--no-ff` so each feature is
  revertable.

### Wave plan

| Wave | Agents (parallel) | Why they can run together |
| ---- | ----------------- | ------------------------- |
| 0 | 1 agent: **P0-1 + A0** (vanilla reconciliation + expansion packs); 1 agent: **P0-2 + P0-3** (finalize versions + sha1 lookup); 1 agent: **P0-4 + P0-5** (activation lock + sweep items) | All backend. Overlap risk on `packs.rs` — mitigated: wave-0 agents get "additive-only in `packs.rs`, new functions + signatures, no refactors of existing fns you weren't assigned". Main agent resolves the (small) merge order: P0-1 first. |
| 1 | 1 agent: **A1** (watcher, backend + `events.ts`); 1 agent: **A2** (reverse deps); 1 agent: **A4** (orphans/size) | Distinct service files (`watcher.rs` new, `resolver.rs`+uninstall flow, `mod_store.rs` scan section). Frontend touchpoints are different pages. |
| 2 | 1 agent: **A5** (update pill + popover + manifest script); 1 agent: **A3** (changelog, backend first then VersionsModal) | A5 owns `App.tsx`/Sidebar/scripts; A3 owns `portal_client.rs`/VersionsModal. No overlap. |
| 3 | 1 agent: **A6** (command palette) — frontend-only, after waves 1–2 merged so it can register their commands too | Sequential by design; also the buffer wave. |

- Tier B items are dispatched the same way as single-agent tasks when their
  turn comes (B3 after wave 0 since it touches the activation lock).
- The **main agent does not implement in parallel**; it reviews each branch
  (`git diff main...branch`), checks the constraint list, merges, and runs
  the combined `cargo test` + `pnpm build` after each merge.
- UI-heavy branches (A5, A6) go through the visual acceptance pass (rendered
  screenshots + judge) before merge, not after.
- If an agent's branch fails review twice, the main agent takes the task
  over directly — don't debug a subagent in a loop.

### What stays manual (no agent)

- The P0-1 root-cause comment and the `ASSUMPTION (...)` verification hits
  against the live portal API (changelog endpoint, auth download contract,
  sha1 field) — these need judgment and a human-checkable paper trail.
- Phase 7 cross-platform install testing and Phase 8 RC validation —
  physical install + updater proof, not parallelizable.
- Release notes, README, and the launch posts (Part IV).

## Part III — Engineering spine (from the v1 plan, updated)

Unchanged from [docs/1.0-release-plan.md](1.0-release-plan.md) — restated with
the deltas this plan introduces:

1. **Phase 3 finisher** — prove the auto-updater end-to-end with a signed
   build + hand-crafted `latest.json`. Still the biggest unknown. Do it
   *before* starting the waves so it can't be squeezed out; A5 sits on top of
   the same manifest.
2. **Phase 2e leftover** — installer-level icon verification rides along with
   Phase 7.
3. **Phase 6 quality pass** — extended: the flow matrix gains the Part 0
   regressions (vanilla with unlisted expansion zips, wrong-version finalize,
   back-to-back pack/vanilla toggles), plus watcher-under-Factorio-writes,
   orphan cleanup on a real messy dir, palette keyboard-only pass, update
   popover with reduced-motion on.
4. **Phase 7 cross-platform** — adds the A1 watcher smoke test per OS;
   otherwise identical (NSIS/MSI, DMG Gatekeeper path, AppImage/deb, 500-zip
   torture).
5. **Phase 8 / 9** — pipeline dry run, `v1.0.0-rc.N`, release. Identical.

Performance budgets (Phase 6a) stay as written; the only new budgets are
"external change → Installed list refreshed < 1.5 s after the debounce" and
"update popover interactive < 100 ms after click".

## Part IV — Launch plan

The release is a product moment, not just a tag.

- **Codename the release line.** 1.0 = "Conveyor" (fits the warm-stone/industrial
  identity; future minors: "Assembler", "Inserter", "Logistics"). Shows up in
  release notes title and the Dashboard version line. Cheap, memorable.
- **Assets:** 90-second GIF/short video — browse → install plan → pack switch
  → launch. Plus the three README screenshots from Phase 9. The update pill +
  release-notes popover gets its own close-up shot — it photographs well.
- **Channels, in order:** r/factorio (mod showcase post, Friday EU evening is
  peak), official Factorio forums "Mods" board, the Factorio Discord
  #showcase, GitHub Topics (`factorio`, `mod-manager`). Lead with the two
  differentiators: dependency plan review and pack switching; be upfront
  about the mirror + SHA1 story (this community rewards honesty about trust).
- **Release notes** from `.github/RELEASE_NOTES_TEMPLATE.md` gain a "What is
  Axial" section for the Reddit/forums crowd (the release page is the landing
  page) — and its body is what `generate-updater-manifest.mjs` feeds into the
  in-app notes popover, so write it for both audiences at once.
- **Post-launch loop:** label every first-issue `1.0-feedback`; watch the
  updater's `latest.json` download counts as a soft adoption metric.

## Part V — Cut order (decided now, not in a panic)

1. A6 (palette) — polish.
2. Tier B remainder — B3 first kept, then B4, then B1, then B2.
3. A5 animation polish (ship the pill/popover static, animations behind a
   flag) — but never the notes data plumbing.
4. Phase 7 shrinks to platforms actually testable (per v1 plan).
5. **Never cut:** Part 0 fixes (all of them — they are correctness),
   SHA1 verification, updater proof, Phase 6b bug hunt, Phase 8 RC validation.

If everything holds, ~2 of the 4 Tier B items ship. That's a good 1.0.
