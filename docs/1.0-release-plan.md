# Axial 1.0 Release Plan

Created 2026-09-12, starting from v0.2.0 (tagged, redesign already on `main`).
The feature set is 1.0-shaped; what remains is release engineering and trust.
Work top to bottom — code changes first, then validation, then the release.

Estimate: ~2–3 weeks of focused work. If cuts are needed: Phase 3 can degrade
to documented bypass instructions, Phase 5 to the platforms actually testable.
Do **not** cut Phase 1 (integrity) or Phase 6 (pipeline validation).

## Phase 1 — SHA1 verification of downloads (~2–3 days)

Goal: a tampered or wrong file from the community mirror cannot reach the mods
directory. Today `verify_mod_zip_sync` (`downloader.rs`) only checks the zip's
own `info.json` name/version — a malicious file passes trivially. The official
portal publishes a SHA1 per release; compare against it.

- [ ] Confirm the field against the live API first (repo convention: verify
      upstream assumptions, record as an `ASSUMPTION (...)` comment):
      `https://mods.factorio.com/api/mods/<name>` → `releases[].sha1`.
- [ ] `models.rs`: add `sha1: Option<String>` to `ModRelease` (camelCase wire
      format unchanged).
- [ ] `portal_client.rs`: parse `sha1` on `PortalRelease` with
      `#[serde(default)]` — tolerant, like every other DTO field.
- [ ] Thread it to the queue: `DownloadQueue::enqueue` takes only
      `(name, version)` today; add `expected_sha1: Option<String>`. Update all
      call sites: install command, version switch, pack-activation finalize
      (`packs.rs`), crash re-recovery. Sites holding `ModDetails` pass it;
      recovery falls back to `None` (existing checks still apply).
- [ ] Verify before rename: in `run_job`, after `download_and_verify` succeeds,
      stream-hash the `.part` file (`sha1` crate, in `spawn_blocking` next to
      the zip check) and compare. Mismatch = **permanent** failure
      (`JobFail::Error(..., false)` — retrying can't change the bytes), delete
      the `.part`, message: "integrity check failed". Missing portal hash →
      warn and proceed with existing checks only.
- [ ] UI: a failed-hash download shows "integrity check failed" in
      `QueueDrawer`, not a generic error.
- [ ] Tests (same-file, per convention): match passes; mismatch is permanent;
      absent hash degrades gracefully.
- [ ] README "A note on downloads": state that archives are verified against
      the portal-published SHA1.

## Phase 2 — Auto-updater (~2–3 days)

Goal: installed users learn about and get 1.0.1 without visiting GitHub.

- [ ] `pnpm tauri signer generate` → private key in GitHub secret
      `TAURI_SIGNING_PRIVATE_KEY`, public key into config.
- [ ] Add `tauri-plugin-updater` (+ `tauri-plugin-process` for restart). In
      `tauri.conf.json`: `"bundle": { "createUpdaterArtifacts": true }`,
      `plugins.updater.endpoints =
      ["https://github.com/<owner>/<repo>/releases/latest/download/latest.json"]`
      + pubkey. Updater is native, CSP unaffected.
- [ ] `build.yml`: set the signing env var; `pnpm tauri build` then emits
      `.sig` files and `latest.json`. Release job ships `latest.json` from one
      platform in the release assets.
- [ ] Frontend: startup check in `App.tsx` → non-blocking "vX available —
      Download & restart" banner; Settings toggle to disable the check.
- [ ] Prove it: signed local build + hand-crafted `latest.json` for a fake
      newer version → app detects, downloads, verifies signature, restarts.

## Phase 3 — Signing decision (~1 day + possibly money)

- [ ] macOS: (a) Apple Developer Program ($99/yr) — Developer ID + notarization
      wired into `build.yml`; or (b) unsigned + documented right-click → Open
      bypass. (a) is what a 1.0 deserves if budget allows.
- [ ] Windows: unsigned triggers SmartScreen. Options: Azure Trusted Signing
      (~$10/mo), OV/EV cert, or document "More info → Run anyway".
- [ ] Linux: nothing needed.
- [ ] Write the user-facing "first launch on your OS" instructions once; reuse
      in README + release notes.

## Phase 4 — First-run and degraded-state UX (~2–3 days)

- [ ] Kill the hardcoded default: `target_factorio_version: "2.0"`
      (`config.rs`). On first launch, seed the target version from detected
      game (`game_detect.rs` reads `data/base/info.json`); fall back to "2.0"
      only when nothing is detected, with a Dashboard banner asking the user
      to confirm.
- [ ] No-Factorio-found flow: every page must say "Factorio not found — set
      your mods folder in Settings" instead of empty stats / errors.
- [ ] Offline/portal-down states: browse, updates check, and install plan all
      degrade to a clear "can't reach the portal" state (resolver already does
      this via the mirror warning — match that pattern elsewhere).
- [ ] Onboarding pass: fresh settings.json → launch → working install in under
      a minute without touching Settings.

## Phase 5 — Real cross-platform testing (~2 days)

CI only proves bundles *build*. For each OS, install the real artifact:

- [ ] Windows (NSIS + MSI): install, launch, mods-dir autodetect (Steam +
      standalone), game version detection, install → enable → uninstall cycle,
      log location.
- [ ] macOS (DMG): Gatekeeper flow per Phase 3 choice, Application Support
      paths. Note: `macos-latest` is ARM — decide between adding an x64 job
      (`macos-13`) and shipping ARM-only with a release-notes caveat.
- [ ] Linux (AppImage + deb): webkit2gtk rendering of the new UI, autodetect
      paths.
- [ ] Torture tests (one platform): 500+ zips cold scan, Factorio running
      during `mod-list.json` writes, cancel mid-download, kill mid-download
      (crash recovery), 50-mod pack activation.
