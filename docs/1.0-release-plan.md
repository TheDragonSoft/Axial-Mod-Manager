# Axial 1.0 Release Plan

Created 2026-09-12, starting from v0.2.0 (tagged, redesign already on `main`).
The feature set is 1.0-shaped; what remains is release engineering, trust, and
one round of UX work. Work top to bottom — code changes first, then
validation, then the release.

Estimate: ~3.5–4 weeks of focused work. If cuts are needed: Phase 4 can degrade
to documented bypass instructions, Phase 7 to the platforms actually testable.
Do **not** cut Phase 1 (integrity) or Phase 8 (pipeline validation).

Per-phase AI-agent handoff prompts: [docs/1.0-agent-prompts.md](1.0-agent-prompts.md).

## Phase 1 — SHA1 verification of downloads (~2–3 days)

Goal: a tampered or wrong file from the community mirror cannot reach the mods
directory. Today `verify_mod_zip_sync` (`downloader.rs`) only checks the zip's
own `info.json` name/version — a malicious file passes trivially. The official
portal publishes a SHA1 per release; compare against it.

Handoff prompt: `docs/phase-1-agent-prompt.md`.

- [x] Confirm the field against the live API first (repo convention: verify
      upstream assumptions, record as an `ASSUMPTION (...)` comment):
      `https://mods.factorio.com/api/mods/<name>` → `releases[].sha1`.
- [x] `models.rs`: add `sha1: Option<String>` to `ModRelease` (camelCase wire
      format unchanged).
- [x] `portal_client.rs`: parse `sha1` on `PortalRelease` with
      `#[serde(default)]` — tolerant, like every other DTO field.
- [x] Thread it to the queue: `DownloadQueue::enqueue` takes only
      `(name, version)` today; add `expected_sha1: Option<String>`. Update all
      call sites: install command, version switch, pack-activation finalize
      (`packs.rs`), crash re-recovery. Sites holding `ModDetails` pass it;
      recovery falls back to `None` (existing checks still apply).
- [x] Verify before rename: in `run_job`, after `download_and_verify` succeeds,
      stream-hash the `.part` file (`sha1` crate, in `spawn_blocking` next to
      the zip check) and compare. Mismatch = **permanent** failure
      (`JobFail::Error(..., false)` — retrying can't change the bytes), delete
      the `.part`, message: "integrity check failed". Missing portal hash →
      warn and proceed with existing checks only.
- [x] UI: a failed-hash download shows "integrity check failed" in
      `QueueDrawer`, not a generic error.
- [x] Tests (same-file, per convention): match passes; mismatch is permanent;
      absent hash degrades gracefully.
- [x] README "A note on downloads": state that archives are verified against
      the portal-published SHA1.

## Phase 2 — UX round: installed expansion, pack switch + Vanilla, launch button, auto game version, app icon ✅ (~4–5 days)

Five user-facing changes, decided 2026-09-12 (screenshots reviewed). Build all
UI from `components/ui/` primitives; keep commands thin; backend logic in
`core/services/`.

### 2a. Expandable installed rows

Click a row on the Installed page and it expands to show the mod's description.

- [x] `pages/InstalledPage.tsx`: rows become clickable accordions — chevron
      affordance, single row expanded at a time, Escape/collapse on second
      click, keyboard accessible.
- [x] Description source: portal `ModDetails.summary` via the existing details
      command (backend caches; mirror enrichment adds per-release deps).
      Lazy-fetch on first expand; cache resolved summaries in a small Zustand
      store following the `lib/thumbnails.ts` + `useThumbnailStore` pattern.
      (Shipped as `lib/summaries.ts` + `useSummaryStore`.)
- [x] Degraded states: show a spinner skeleton while fetching; on failure
      (offline) show a muted "description unavailable" line, never an error
      toast. Expanded area also carries the row's secondary facts (installed
      path size, deps count, Factorio version) where cheap.
- [x] Rows already have a enable/disable Toggle, versions and delete buttons —
      clicks on those must not toggle expansion (stopPropagation).

### 2b. Packs: activation switch + built-in Vanilla pack

Replace the per-pack **Activate** button with a switch, and add a built-in
**Vanilla** pack. Decisions (product-level, do not relitigate silently):

- **Exactly one pack is active at any time.** Activating a pack already
  reconciles the whole mod-list to that pack's target, so the switches behave
  like a radio group rendered as switches.
- **Turning the active pack's switch OFF activates Vanilla** (all mods
  disabled) — a switch must always be switchable, and "off" needs a defined
  state. Vanilla is that off-state.
- **Vanilla is a built-in pseudo-pack**: reserved id `vanilla`, always pinned
  first on the Packs page and in Quick Access, not deletable or exportable.

- [x] Backend: activation of Vanilla = write `mod-list.json` with every mod
      disabled except `base` (Factorio requires `base` enabled). New service
      function in `mod_store.rs` + thin command; unit test in `mod_store.rs`
      asserting `base` survives and others flip to disabled. (`disable_all_mods`
      + `activate_vanilla` command.)
- [x] Backend: track the active pack — add `active_pack_id: Option<String>`
      to `Config` (atomic write as usual), set on activation finalize
      (including `vanilla`), returned with settings so the UI can render
      switch states. `packs.rs` sets it in the finalize path.
      (`persist_active_pack` + `settings-changed`.)
- [x] `components/packs/PackCard.tsx` + `pages/PacksPage.tsx`: swap the
      Activate button for the `Toggle` primitive, driven by
      `active_pack_id`; flipping any switch goes through the existing
      confirm/plan flow for the target pack (Vanilla included — it disables
      mods, so confirm first via `useConfirm`). *Updated 2026-09-13: the
      confirmation step was deliberately removed (`c8afc37`) — switches
      activate immediately; only Delete still confirms.*
- [x] Sidebar Quick Access: include Vanilla pinned above the user packs;
      green StatusDot marks the active one.
- [x] During a pack download-driven finalize, the target pack's switch shows
      an in-progress state (ProgressBar/Spinner) until `pack-activated`.

### 2c. Launch Factorio button

- [x] Placement: in the `components/Sidebar.tsx` header block, above the
      NAVIGATION section — a full-width primary Button ("Launch Factorio",
      Play icon).
- [x] Backend: new `launch_game` command. Resolution reuses `game_detect.rs`'
      install detection, but the spawn lives in its own small service function
      (game_detect stays read-only per AGENTS.md; this feature deliberately
      introduces the one process spawn). Binary per OS:
      `<install>/bin/x64/factorio.exe` (Windows), `.../bin/x64/factorio`
      (Linux), `Factorio.app/Contents/MacOS/factorio` (macOS). Spawn detached
      (`std::process::Command::spawn`, don't wait). Launch the binary directly
      — Factorio's Steam build runs fine without the Steam client.
- [x] Not-found state: button disabled with a tooltip "Factorio not found —
      set the game folder in Settings"; success adds a Dashboard activity
      entry.
- [x] Test: executable-path resolution per OS as a pure function with inline
      fixtures (repo convention).

### 2d. Auto-detected target Factorio version (remove the selector)

- [x] Remove the Compatibility / "Target Factorio Version" Select from
      `pages/SettingsPage.tsx` (the whole Compatibility panel, per screenshot).
- [x] `config.rs`: `target_factorio_version` stays as a field but becomes a
      cache of the last detection — at startup and whenever `game_dir` changes,
      `game_detect` reads the version from `data/base/info.json` and persists
      it. When detection fails, keep the last cached value (current default
      "2.0" only on true first run).
- [x] All readers (`updates.rs` check, browse filtering, deps command,
      Dashboard) keep reading config — no IPC contract change; `settings-changed`
      still carries the value so `useAppStore.targetFactorioVersion` and every
      consumer (`InstallModal`, `BrowsePage`, `InstalledPage`,
      `ModDetailsModal`) work unchanged.
- [x] Dashboard: label the version as auto-detected ("Factorio 2.0.x
      (detected)"); if detection failed, show a muted "set your game folder"
      hint linking to Settings.

### 2e. App icon

The app still ships the **default Tauri scaffold icon** (teal/yellow swirl —
`src-tauri/icons` has only the scaffold commit, `fb3c42c`). Replace it with
real branding.

- [x] Design the final icon at 1024×1024 (SVG or PNG): warm-stone dark tile
      with the green accent, consistent with the sidebar logo tile and the
      app palette. Keep the motif readable at 16–32 px (taskbar/favicon
      sizes).
- [x] Regenerate all bundle icons from the source:
      `pnpm tauri icon <source.png>` overwrites the `.ico`/`.icns`/png set
      and the Windows Store logos.
- [x] Reuse the mark in-app: the Sidebar "Axial" header currently renders a
      letter "A" tile — swap it for the real asset.
- [ ] Installer-level verification (taskbar/window icon, NSIS shortcut, DMG)
      happens during Phase 7 cross-platform testing.

## Phase 3 — Auto-updater (~2–3 days) — implemented; end-to-end proof pending

Goal: installed users learn about and get 1.0.1 without visiting GitHub.

- [x] `pnpm tauri signer generate` → private key in GitHub secret
      `TAURI_SIGNING_PRIVATE_KEY`, public key into config.
- [x] Add `tauri-plugin-updater` (+ `tauri-plugin-process` for restart). In
      `tauri.conf.json`: `"bundle": { "createUpdaterArtifacts": true }`,
      `plugins.updater.endpoints =
      ["https://github.com/<owner>/<repo>/releases/latest/download/latest.json"]`
      + pubkey.
- [x] `build.yml`: set the signing env var; `pnpm tauri build` then emits
      `.sig` files and `latest.json` (`scripts/generate-updater-manifest.mjs`).
      Release job ships `latest.json` from one platform in the release assets.
- [x] Frontend: startup check in `App.tsx` → non-blocking "vX available —
      Download & restart" banner; Settings toggle to disable the check.
      (Also respects a dismissed version via `Config.dismissed_update_version`.)
- [ ] Prove it: signed local build + hand-crafted `latest.json` for a fake
      newer version → app detects, downloads, verifies signature, restarts.

## Phase 6 — Quality pass: performance, bugs, UI polish (~3–4 days)

One hardening phase, three subsections, run on **release builds** after all
feature work (Phases 1–2) has landed. File every finding as a GitHub issue
first, then fix; anything not fixed for 1.0 gets a `post-1.0` label and a
known-issues note in the release.

### 6a. Performance check-up ✅

Measure first, then fix against budgets — no blind optimization.

- [x] Define and measure budgets: startup to interactive (<2 s, release
      build), cold installed scan (500+ zips), portal search round-trip to
      rendered results, download throughput vs raw bandwidth, idle memory
      after 30 min. (Completed; documented in `docs/perf-report-1.0.md`.)
- [x] Backend: confirm the mtime zip cache + parallel cold scan hold up at
      scale (shipped in `bcde8c4`); check `download-updated` event frequency
      on fast downloads — throttle progress emissions if the UI re-renders
      per chunk. (Bulk cache insert added; 500 zips scanned in 97.96 ms cold /
      9.15 ms warm.)
- [x] Frontend: production build (`pnpm build`) — check bundle size, add
      code-splitting for portal-heavy pages if the initial chunk is fat; audit
      Zustand selector usage for wide re-renders driven by queue events.
      (Pages code-split with React.lazy/Suspense reducing initial chunk by 22%;
      QueueDrawer isolated with QueueItemList to prevent offscreen re-renders.)
- [x] Deliverable: a short perf report in `docs/` with before/after numbers;
      only fix what misses a budget. (`docs/perf-report-1.0.md`.)

### 6b. Bug hunt and fixes

Systematic end-to-end exercise of every flow.

- [ ] Full flow matrix: browse → install (with plan) → expand row →
      enable/disable → version switch → pack create → activate switch →
      Vanilla → uninstall → bulk update; settings paths (mods-dir override,
      game-dir change, log level).
- [ ] Edge cases: kill mid-download (crash recovery), portal unreachable,
      mirror unreachable, 500+ mod dir, Factorio running during writes, mods
      with spaces/unicode in names, very long titles (truncation), enqueueing
      the same mod twice, pack activation racing a manual download.
- [ ] Audit `logs/axial.log` at debug level during the whole pass — every
      warn/error trace becomes an issue.
- [ ] Fix P0/P1 for 1.0; label the rest `post-1.0`.

### 6c. UI improvements

A consistency sweep against the design system in `components/ui/` — no new
features here.

- [ ] Every page builds on the shared primitives — no inlined class-string
      one-offs; empty states via `EmptyState`, loading via `Spinner` or
      skeletons.
- [ ] Accessibility: focus-visible rings, tab order, Enter/Space activation
      for the installed rows (Phase 2a), aria-labels on icon-only buttons
      (delete, versions).
- [ ] Muted-text contrast on the stone palette, long-title truncation, dark
      themed scrollbars, consistent hover/active states on cards and rows.
- [ ] Transition polish: subtle expand/collapse for Phase 2a rows, switch
      toggles, modal enter — restrained, matching the existing design.

## Phase 7 — Real cross-platform testing (~2 days)

CI only proves bundles *build*. For each OS, install the real artifact:

- [ ] Windows (NSIS + MSI): install, launch, SmartScreen first-launch flow verification
      ("More info → Run anyway"), mods-dir autodetect (Steam + standalone),
      game version detection, install → enable → uninstall cycle, log location,
      Launch Factorio button (Phase 2c).
- [ ] macOS (DMG): Gatekeeper first-launch flow verification per Phase 4 choice
      (right-click → Open bypass, or notarized launch if certs configured),
      Application Support paths. Note: `macos-latest` is ARM — decide between
      adding an x64 job (`macos-13`) and shipping ARM-only with a release-notes
      caveat.
- [ ] Linux (AppImage + deb): executable permission (`chmod +x`) / first-launch
      flow verification, webkit2gtk rendering of the new UI, autodetect paths.
- [ ] Torture tests (one platform): 500+ zips cold scan, Factorio running
      during `mod-list.json` writes (including pack-switch and Vanilla
      activation), cancel mid-download, kill mid-download (crash recovery),
      50-mod pack activation.
- [ ] Activation-lock torture (P0-4): pack switch and Vanilla clicked
      back-to-back while a pack finalize is still in flight — Vanilla must
      win (no re-persist of the pack's `active_pack_id` over `"vanilla"`, no
      interleaved `mod-list.json` writes).
