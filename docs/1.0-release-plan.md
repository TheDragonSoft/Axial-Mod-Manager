# Axial 1.0 Release Plan

Created 2026-09-12, starting from v0.2.0 (tagged, redesign already on `main`).
The feature set is 1.0-shaped; what remains is release engineering, trust, and
one round of UX work. Work top to bottom — code changes first, then
validation, then the release.

Estimate: ~3 weeks of focused work. If cuts are needed: Phase 4 can degrade to
documented bypass instructions, Phase 6 to the platforms actually testable.
Do **not** cut Phase 1 (integrity) or Phase 7 (pipeline validation).

## Phase 1 — SHA1 verification of downloads (~2–3 days)

Goal: a tampered or wrong file from the community mirror cannot reach the mods
directory. Today `verify_mod_zip_sync` (`downloader.rs`) only checks the zip's
own `info.json` name/version — a malicious file passes trivially. The official
portal publishes a SHA1 per release; compare against it.

Handoff prompt: `docs/phase-1-agent-prompt.md`.

- [ ] Confirm the field against the live API first (repo convention: verify
      upstream assumptions, record as an `ASSUMPTION (...)` comment):
      `https://mods.factorio.com/api/mods/<name>` → `releases[].sha1`.
- [ ] `models.rs`: add `sha1: Option<String>` to `ModRelease` (camelCase wire
      format unchanged).
- [ ] `portal_client.rs`: parse `sha1` on `PortalRelease` with
      `#[serde(default)]` — tolerant, like every other DTO field.
- [ ] Thread it to the queue: `DownloadQueue::enqueue` takes only
      `(name, version)` today; add `expected_sha1: Option<String>`. Update all
      call sites: install command, version switch, pack-activation finalize
      (`packs.rs`), crash re-recovery. Sites holding `ModDetails` pass it;
      recovery falls back to `None` (existing checks still apply).
- [ ] Verify before rename: in `run_job`, after `download_and_verify` succeeds,
      stream-hash the `.part` file (`sha1` crate, in `spawn_blocking` next to
      the zip check) and compare. Mismatch = **permanent** failure
      (`JobFail::Error(..., false)` — retrying can't change the bytes), delete
      the `.part`, message: "integrity check failed". Missing portal hash →
      warn and proceed with existing checks only.
- [ ] UI: a failed-hash download shows "integrity check failed" in
      `QueueDrawer`, not a generic error.
- [ ] Tests (same-file, per convention): match passes; mismatch is permanent;
      absent hash degrades gracefully.
- [ ] README "A note on downloads": state that archives are verified against
      the portal-published SHA1.

## Phase 2 — UX round: installed expansion, pack switch + Vanilla, launch button, auto game version (~3–4 days)

Five user-facing changes, decided 2026-09-12 (screenshots reviewed). Build all
UI from `components/ui/` primitives; keep commands thin; backend logic in
`core/services/`.

### 2a. Expandable installed rows

Click a row on the Installed page and it expands to show the mod's description.

- [ ] `pages/InstalledPage.tsx`: rows become clickable accordions — chevron
      affordance, single row expanded at a time, Escape/collapse on second
      click, keyboard accessible.
- [ ] Description source: portal `ModDetails.summary` via the existing details
      command (backend caches; mirror enrichment adds per-release deps).
      Lazy-fetch on first expand; cache resolved summaries in a small Zustand
      store following the `lib/thumbnails.ts` + `useThumbnailStore` pattern.
- [ ] Degraded states: show a spinner skeleton while fetching; on failure
      (offline) show a muted "description unavailable" line, never an error
      toast. Expanded area also carries the row's secondary facts (installed
      path size, deps count, Factorio version) where cheap.
- [ ] Rows already have a enable/disable Toggle, versions and delete buttons —
      clicks on those must not toggle expansion (stopPropagation).

### 2b. Packs: activation switch + built-in Vanilla pack

Replace the per-pack **Activate** button with a switch, and add a built-in
**Vanilla** pack. Decisions (product-level, do not relitigate silently):

- **Exactly one pack is active at any time.** Activating a pack already
  reconciles the whole mod-list to that pack's target, so the switches behave
  like a radio group rendered as switches.
- **Turning the active pack's switch OFF activates Vanilla** (all mods
  disabled) — a switch must always be switchable, and "off" needs a defined
  state. Vanilla is that off-state.
- **Vanilla is a built-in pseudo-pack**: reserved id `vanilla`, always pinned
  first on the Packs page and in Quick Access, not deletable or exportable.

- [ ] Backend: activation of Vanilla = write `mod-list.json` with every mod
      disabled except `base` (Factorio requires `base` enabled). New service
      function in `mod_store.rs` + thin command; unit test in `mod_store.rs`
      asserting `base` survives and others flip to disabled.
- [ ] Backend: track the active pack — add `active_pack_id: Option<String>`
      to `Config` (atomic write as usual), set on activation finalize
      (including `vanilla`), returned with settings so the UI can render
      switch states. `packs.rs` sets it in the finalize path.
- [ ] `components/packs/PackCard.tsx` + `pages/PacksPage.tsx`: swap the
      Activate button for the `Toggle` primitive, driven by
      `active_pack_id`; flipping any switch goes through the existing
      confirm/plan flow for the target pack (Vanilla included — it disables
      mods, so confirm first via `useConfirm`).
- [ ] Sidebar Quick Access: include Vanilla pinned above the user packs;
      green StatusDot marks the active one.
- [ ] During a pack download-driven finalize, the target pack's switch shows
      an in-progress state (ProgressBar/Spinner) until `pack-activated`.

### 2c. Launch Factorio button

- [ ] Placement: in the `components/Sidebar.tsx` header block, above the
      NAVIGATION section — a full-width primary Button ("Launch Factorio",
      Play icon).
- [ ] Backend: new `launch_game` command. Resolution reuses `game_detect.rs`'
      install detection, but the spawn lives in its own small service function
      (game_detect stays read-only per AGENTS.md; this feature deliberately
      introduces the one process spawn). Binary per OS:
      `<install>/bin/x64/factorio.exe` (Windows), `.../bin/x64/factorio`
      (Linux), `Factorio.app/Contents/MacOS/factorio` (macOS). Spawn detached
      (`std::process::Command::spawn`, don't wait). Launch the binary directly
      — Factorio's Steam build runs fine without the Steam client.
- [ ] Not-found state: button disabled with a tooltip "Factorio not found —
      set the game folder in Settings"; success adds a Dashboard activity
      entry.
- [ ] Test: executable-path resolution per OS as a pure function with inline
      fixtures (repo convention).

### 2d. Auto-detected target Factorio version (remove the selector)

- [ ] Remove the Compatibility / "Target Factorio Version" Select from
      `pages/SettingsPage.tsx` (the whole Compatibility panel, per screenshot).
- [ ] `config.rs`: `target_factorio_version` stays as a field but becomes a
      cache of the last detection — at startup and whenever `game_dir` changes,
      `game_detect` reads the version from `data/base/info.json` and persists
      it. When detection fails, keep the last cached value (current default
      "2.0" only on true first run).
- [ ] All readers (`updates.rs` check, browse filtering, deps command,
      Dashboard) keep reading config — no IPC contract change; `settings-changed`
      still carries the value so `useAppStore.targetFactorioVersion` and every
      consumer (`InstallModal`, `BrowsePage`, `InstalledPage`,
      `ModDetailsModal`) work unchanged.
- [ ] Dashboard: label the version as auto-detected ("Factorio 2.0.x
      (detected)"); if detection failed, show a muted "set your game folder"
      hint linking to Settings.

## Phase 3 — Auto-updater (~2–3 days)

Goal: installed users learn about and get 1.0.1 without visiting GitHub.

- [ ] `pnpm tauri signer generate` → private key in GitHub secret
      `TAURI_SIGNING_PRIVATE_KEY`, public key into config.
- [ ] Add `tauri-plugin-updater` (+ `tauri-plugin-process` for restart). In
      `tauri.conf.json`: `"bundle": { "createUpdaterArtifacts": true }`,
      `plugins.updater.endpoints =
      ["https://github.com/<owner>/<repo>/releases/latest/download/latest.json"]`
      + pubkey. Updater is native, CSP unaffected.
- [ ] `build.yml`: set the signing env var; `pnpm tauri build` then emits
      `.sig` files and `latest.json`. Release job ships `latest.json` from one
      platform in the release assets.
- [ ] Frontend: startup check in `App.tsx` → non-blocking "vX available —
      Download & restart" banner; Settings toggle to disable the check.
- [ ] Prove it: signed local build + hand-crafted `latest.json` for a fake
      newer version → app detects, downloads, verifies signature, restarts.

## Phase 4 — Signing decision (~1 day + possibly money)

- [ ] macOS: (a) Apple Developer Program ($99/yr) — Developer ID + notarization
      wired into `build.yml`; or (b) unsigned + documented right-click → Open
      bypass. (a) is what a 1.0 deserves if budget allows.
- [ ] Windows: unsigned triggers SmartScreen. Options: Azure Trusted Signing
      (~$10/mo), OV/EV cert, or document "More info → Run anyway".
- [ ] Linux: nothing needed.
- [ ] Write the user-facing "first launch on your OS" instructions once; reuse
      in README + release notes.

## Phase 5 — First-run and degraded-state UX (~2–3 days)

- [ ] No-Factorio-found flow: every page must say "Factorio not found — set
      your mods folder in Settings" instead of empty stats / errors. (The
      target-version side of this is handled in Phase 2d.)
- [ ] Offline/portal-down states: browse, updates check, and install plan all
      degrade to a clear "can't reach the portal" state (resolver already does
      this via the mirror warning — match that pattern elsewhere).
- [ ] Onboarding pass: fresh settings.json → launch → working install in under
      a minute without touching Settings.

## Phase 6 — Real cross-platform testing (~2 days)

CI only proves bundles *build*. For each OS, install the real artifact:

- [ ] Windows (NSIS + MSI): install, launch, mods-dir autodetect (Steam +
      standalone), game version detection, install → enable → uninstall cycle,
      log location, Launch Factorio button (Phase 2c).
- [ ] macOS (DMG): Gatekeeper flow per Phase 4 choice, Application Support
      paths. Note: `macos-latest` is ARM — decide between adding an x64 job
      (`macos-13`) and shipping ARM-only with a release-notes caveat.
- [ ] Linux (AppImage + deb): webkit2gtk rendering of the new UI, autodetect
      paths.
- [ ] Torture tests (one platform): 500+ zips cold scan, Factorio running
      during `mod-list.json` writes (including pack-switch and Vanilla
      activation), cancel mid-download, kill mid-download (crash recovery),
      50-mod pack activation.
