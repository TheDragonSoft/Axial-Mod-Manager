# Axial 1.0 — AI Agent Prompts, Phase by Phase

Handoff prompts for executing [docs/1.0-release-plan.md](1.0-release-plan.md)
with an AI coding agent (ZCode, Claude Code, Cursor, …).

**How to use**

1. Run phases **in order, one agent session per phase** (sub-phases 2a–2e are
   their own sessions). Review and commit between phases — later prompts
   assume earlier ones landed on `main`.
2. For each session, paste the **Shared context block** below, then the
   phase's prompt block.
3. Phase 0 (repo hygiene) is **done** — no prompt. Phase 1 also exists as a
   standalone file (`docs/phase-1-agent-prompt.md`, same content).

---

## Shared context block — prepend to every phase prompt

```text
You are working on Axial, a Tauri 2 desktop mod manager for Factorio
(Rust backend, React 19 + TypeScript frontend). Work in the repo root on
`main`.

REQUIRED READING (in order):
1. AGENTS.md — architecture, conventions, recipes. Follow it exactly.
2. docs/1.0-release-plan.md — the roadmap; your task is the phase named below.

ENVIRONMENT:
- Windows dev machine; shell is cmd.exe — no grep/head/ls; use `git grep`, `dir`.
- Gates before you report done: `cargo test --manifest-path src-tauri/Cargo.toml`
  (all existing tests green) and, if you touched src/, `pnpm build` (tsc).
  If cargo complains about a missing frontendDist, run `pnpm build` first.
- Commit your work with a conventional-commit message once the gates are green.

HOUSE RULES (from AGENTS.md, restated):
- src-tauri/src/models.rs is the single source of truth for IPC types
  (camelCase serde); the frontend mirrors it in src/types.ts and calls it
  through typed wrappers in src/lib/api.ts.
- Commands stay thin (parse args → service → map errors); logic lives in
  src-tauri/src/core/services/.
- Errors are AppError {kind, message}; never invent ad-hoc error shapes.
- Atomic writes (temp file + rename) for any persisted file; .part + rename
  for downloads.
- Rust tests live in the same file as the logic they test.
- Verify upstream/API assumptions against the live service and record them as
  `ASSUMPTION (...)` comments; never trust upstream data in file paths.
- Build UI from src/components/ui/ primitives; palette is warm stone +
  #00CC46 accent only (no zinc/slate, no new accent hues); icons lucide-react.

WORKING AGREEMENT:
- Design decisions in the phase brief are settled — implement them as
  specified. If you believe one is wrong, implement it anyway (unless factually
  impossible) and explain your concern in the final report.
- Stay inside the phase's scope; out-of-scope items are listed per phase.
- Final report: files changed and why, actual test/build output, deviations
  with reasoning, and anything the user must do manually.
```

## Phase 1 — SHA1 verification of downloads

```text
Task: Phase 1 — SHA1 verification of mod downloads.

Step 0 — verify the upstream assumption FIRST:
curl -s https://mods.factorio.com/api/mods/bottleneck
Confirm each object in `releases` carries a `sha1` (40-char lowercase hex).
Record the finding as an `ASSUMPTION (...)` comment on the new DTO field.
If no sha1-like field exists under any plausible name, STOP and report —
do not build verification with no source of truth.

1. Types: add `sha1: Option<String>` to `ModRelease` (models.rs, ~line 85) and
   `#[serde(default)] pub sha1: Option<String>` to `PortalRelease`
   (portal_client.rs, ~line 39); carry it through `map_release` (~line 231).
   Confirm the mirror enrichment path (mirror_client.rs, PortalWithMirrorDeps)
   preserves the portal hash. Add `sha1?: string | null` to `ModRelease` in
   src/types.ts. No UI display required.
2. Queue plumbing: add `expected_sha1: Option<String>` to
   `DownloadQueue::enqueue` (downloader.rs:79). Update ALL THREE call sites:
   - commands/downloads.rs:19 — preferred: accept the hash as an optional IPC
     arg from the frontend (InstallModal already holds the picked release's
     details; no extra fetch). Follow the five-step recipe if you change the
     command surface.
   - packs.rs:297 — pass the hash when the plan holds release info, else None.
   - lib.rs:115 — crash-recovery re-enqueue: pass None (degradation path).
3. Verification: add `verify_sha1_sync(path, expected)` — stream the file in
   chunks (`sha1` crate in Cargo.toml), compare lowercase hex. Call it inside
   `spawn_blocking` right after `verify_mod_zip` succeeds (~line 340, in
   download_and_verify). Mismatch → JobFail::Error("integrity check failed: …",
   false) — verify run_job's retry loop treats the second field as the
   transient flag so this does NOT retry, and that the failure branch deletes
   the .part file. Missing/empty expected hash → tracing::warn!, proceed with
   existing checks.
4. UI: the error reaches QueueDrawer via the existing download-updated event —
   no new events/stores; just ensure the string renders readably.
5. Tests (create `mod tests` in downloader.rs, same-file convention): match
   passes; mismatch is permanent; comparison case-insensitive; empty/absent
   expectation is a no-op. Prefer pure functions over mocks; no live-server
   tests.
6. Docs: README "A note on downloads" — one sentence on SHA1 verification.
   Tick the Phase 1 checkboxes in docs/1.0-release-plan.md.

Out of scope: portal auth/official downloads, mirror changes, pack format,
JS test infra, version bumps, CI.
Suggested commit: `feat(downloader): verify downloads against portal-published sha1`.
```

### 2b — Pack activation switch + built-in Vanilla pack

```text
Task: Phase 2b — replace the per-pack Activate button with a switch and add a
built-in Vanilla pack.

Settled product decisions (do not relitigate): exactly one pack is active at
any time (activation reconciles the whole mod-list, so switches behave as a
radio group); turning the active pack's switch OFF activates Vanilla; Vanilla
is a built-in pseudo-pack — reserved id `vanilla`, pinned first on the Packs
page and in Quick Access, not deletable or exportable.

Backend:
1. mod_store.rs: service function that writes mod-list.json with every mod
   disabled EXCEPT `base` (Factorio requires base enabled). Thin command +
   lib.rs registration + api.ts wrapper (five-step recipe). Unit test in
   mod_store.rs: base stays enabled, others flip to disabled, the file stays
   valid for Factorio.
2. Config (config.rs): add `active_pack_id: Option<String>` (camelCase wire).
   packs.rs finalize sets it (including `vanilla`); the settings command
   returns it; settings-changed carries it. Atomic write as usual.
Frontend:
3. PackCard.tsx / PacksPage.tsx: replace Activate with the Toggle primitive,
   driven by active_pack_id. Flipping any switch runs the existing
   confirm/plan flow for the target pack (Vanilla included — it disables
   mods; use useConfirm). Only one switch can be on. While a pack's
   download-driven finalize is running, its switch shows an in-progress state
   until `pack-activated` lands.
4. Sidebar Quick Access: pin Vanilla above the user packs; StatusDot marks
   the active one; clicking behaves like the switch.

Out of scope: pack manifest format changes, altering activation
reconciliation logic.
Suggested commit: `feat(packs): activation switch, active-pack state, built-in Vanilla pack`.
```

## Phase 3 — Auto-updater

```text
Task: Phase 3 — in-app auto-updater (tauri-plugin-updater).

1. Keys: run `pnpm tauri signer generate`. Write the private key to a local
   UNTRACKED path — never commit or print it. Put the public key into
   tauri.conf.json. In your report, give the user one instruction: add
   TAURI_SIGNING_PRIVATE_KEY (+ its password) as GitHub Actions secrets.
2. Config: add tauri-plugin-updater + tauri-plugin-process (Rust deps, JS
   packages, plugin registration in lib.rs). In tauri.conf.json:
   "bundle": { "createUpdaterArtifacts": true } and
   plugins.updater.endpoints =
   ["https://github.com/<owner>/<repo>/releases/latest/download/latest.json"]
   (derive owner/repo from the git remote) plus the public key. CSP is
   unaffected (updater is native).
3. build.yml: set TAURI_SIGNING_PRIVATE_KEY env (from secrets) on the build
   step so `pnpm tauri build` emits .sig files and latest.json; ship
   latest.json from ONE platform in the release job's assets.
4. Frontend: startup check in App.tsx → non-blocking "vX available — Download
   & restart" banner (Panel + Button primitives); Settings toggle to disable
   the check, persisted in Config via the standard recipes.
5. Prove locally: signed local build + hand-crafted latest.json pointing at a
   fake newer version → the app detects, downloads, verifies the signature,
   and restarts. Document the proof. If the GitHub secret isn't set yet, CI
   verification defers to Phase 8 — note it.

Out of scope: auto-install without consent, force-update UX.
Suggested commit: `feat: in-app auto-updater`.
```

budget; no blind optimization. Measure on RELEASE builds (`pnpm tauri build`

   queue events; the mtime zip cache + parallel cold scan (bcde8c4) at scale.
3. Deliverable: docs/perf-report-1.0.md with numbers, fixes applied, and
   what was deliberately left alone. Tests stay green.
